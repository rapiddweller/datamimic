# DATAMIMIC CE 5.0

CE 5.0 makes DATAMIMIC a tool you and your coding agent author with: write an XML project, let Build prove it
against your expectations, then run it for the real data. Errors name the cause, the file and the fix, and the
same seed gives the same rows on every tested platform.

## Highlights

- **Build proves a project before you use it.** `datamimic authoring build` runs the project in a bounded process
  and checks the expectations in `acceptance/build.json`: counts, counts per parent, ranges, fixed and allowed
  values, uniqueness, references between products and row conditions. It answers `ready`, `ready_with_gaps` or
  `rejected`, with evidence: the captured rows, every project file it read with its digest, and the coverage gaps
  it still sees.
- **From an empty folder to data in three steps.** `datamimic authoring init`, `authoring build` and
  `authoring run-project`, or the same through MCP (`datamimic_init`, `datamimic_build`, `datamimic_run_project`).
  `run-project` builds first and refuses writes to a database or another external target unless you allow side
  effects.
- **Built for coding agents.** The Claude Code / Codex plugin connects the DATAMIMIC MCP server and brings the
  skills for the author, build and run loop. Every project tool takes the project path and refuses an oversized
  result with a hint instead of cutting it; `datamimic_version` reports the build protocol the server speaks.
- **Errors that say what to fix.** Errors carry a stable code and a repair hint. Diagnostics name the file, line,
  column, element and attribute, and for an included step the files that include it. Lint catches common traps
  before a run, such as an unknown target, a selector without a count, a seeded script that iterates a set, or a
  step seed that would be ignored.
- **The same seed gives the same rows.** CI proves byte-identical seeded output in eight cells: Linux and Windows,
  Python 3.11 to 3.14, two timezones, newest and lowest dependency versions. Each generator that takes the context
  draws from its own stream, so values in one row no longer repeat each other.
- **More realistic data.** IBANs have the length and check digits of their country, US and DE postal codes keep
  their leading zero, AU, FR and US city data is cleaned, no value starts with a byte-order mark, and weighted
  entity files are drawn by weight, as in EE.
- **Stricter and safer.** Attributes that were silently ignored are refused with a message. Database selector
  values and SQL text stay out of logs and error causes.
- **Python 3.11 to 3.14 and a clearer CLI.** A shorter run log, errors on stderr, help on every command.
  `authoring build` exits `0` ready, `3` ready with gaps and `1` rejected; every command exits `2` on a usage
  error.

## Install

CE 5.0 is not on PyPI yet. Until 5.0.0, install from GitHub `development`
using Python 3.11 or newer; CE 5.0 is tested on 3.11, 3.12, 3.13 and 3.14:

```bash
python -m pip install "datamimic-ce @ git+https://github.com/rapiddweller/datamimic@development"
```

## Upgrade checklist

1. Use Python 3.11 or newer.
2. Regenerate stored seeded output. Seeded values can change for generators that take the context, for Person, City
   and Street of DE, AT, BR, CH and IL, for US and DE postal codes, AU, FR and US cities, and for IBANs.
3. Re-author 4.x intent and scaffold models as projects; XML models keep running. The root `scaffold`, `lint`,
   `dry-run`, `reference` and `capabilities` commands are now under `datamimic authoring`.
4. Give every project at least one expectation in `acceptance/build.json`, and cast CSV text to numbers before a
   `range` expectation.
5. Move attributes that CE used to ignore to where they apply; CE now refuses them.
6. To read a `*.wgt.ent.csv` file row by row, rename it to `.ent.csv`; to sample it, add `weightColumn` and `count`.
7. MCP clients pass the absolute project path in every call. Scripts handle exit codes `2` and `3` and read the
   `Error:` line instead of log lines.

## Breaking changes

### Authoring and Build

- XML is the persisted executable project; DM JSON is transient.
- Project Build replaces persisted Intent/Scaffold authoring. A project is a
  `datamimic.xml` entry, its included steps and `acceptance/build.json`, which holds
  expectations, roles and verification options. A ready Build lists every project
  file it read with its digest.
- Root scaffold/lint/dry-run/reference/capabilities commands move to the typed
  `datamimic authoring` subtree. Legacy Python authoring modules are retired.
- Catalog-backed errors carry stable identity and repair guidance. Some formerly
  generic exceptions now use portable typed exceptions with their native cause.
- A Build with open coverage gaps answers `ready_with_gaps`, and `datamimic authoring build` exits with code `3`.
  A Build that passed its run, but whose `coverage` has an open gap (a product without expectation, an unread
  project data file, a declared sink without a sink check, or no `rngSeed`), no longer answers `ready`. It carries the
  same `artifact`, `assurance`, `evidence`, `coverage`, `verification` and `diagnostics` (one `coverage_gap` warning for
  each gap) and the field `action_required`, for example `Ready with 1 open coverage gap (seeded). Do not report
  success until each gap is fixed or explained.` A Build without a gap stays `ready`. Exit codes of `authoring build`:
  `0` ready, `3` ready_with_gaps, `1` rejected or unreadable input, `2` usage error; the text output shows
  `Status: Ready with gaps`. `ReadyBuild` has a new required field `coverage`; `BuildResult` is
  `ReadyBuild | ReadyWithGapsBuild | RejectedBuild` (discriminator `outcome`). `datamimic_run_project` still runs a
  `ready_with_gaps` Build and returns `build_outcome`, `coverage` and `action_required`. Migration: a client that tests
  `outcome == "ready"` sees a gapped Build as not ready, which is the intent; it shows `action_required` and the
  warnings and does not report success. A client that parses `BuildResult` strictly adds `ReadyWithGapsBuild`.
  The authoring eval counts `ready_with_gaps` as not passed.
- Build refuses an acceptance without expectation. A project that generates at least one product and has no check for
  any product (no entry in `expectations`, and no check derived from literal counts, `product_roles` or
  `acceptance_requirements`) is rejected with `missing_expectation`. Build still runs the project; the diagnostic
  (phase `expectation`, path `acceptance/build.json` / `expectations`) follows the diagnostics of the run, and the
  rejection is an `evidence` rejection. Before, `{"version": "5.0"}` was a valid acceptance for such a project.
  Migration: add one expectation, for example `{"kind": "exact_count", "subject": {"kind": "product",
  "product": "orders"}, "count": 10}`. `datamimic authoring init PROJECT` writes a starter project (`datamimic.xml`
  with `rngSeed`, and `acceptance/build.json` with one expectation) that Build proves as `ready`; it never overwrites
  a file and refuses a symlink. The MCP tool `datamimic_init` does the same through the same writer. `datamimic init PROJECT` writes the same two files from the same scaffold, plus the
  `data/`, `script/`, `output/`, `config/` folders and a README. The `datamimic init` starter is therefore now the
  seeded flat starter (`rngSeed="7"`, product `rows`, 2 rows) with `acceptance/build.json`, no longer the former
  user list, and it overwrites existing starter files only with `--force`.
- A `range` expectation needs numbers (#453). Before, text that looks like a number, such as `"42"` read from a CSV
  column, passed the range and Build answered `ready`. Now Build rejects it: `values for '<field>' in <subject> are
  not numbers; range requires numeric captured values`. Migration: cast the column in the model, for example
  `script="int(amount)"`.

There is no automated migration from the 4.x intent and scaffold models: re-author them as projects (see
[migration](../migrations/authoring-errors.md)). XML models keep running. A ready Build, `compile` support and real
delivery to an external system are separate things, and restricting the targets of a model does not make untrusted
Python in it safe.

### Models and scripts

- Attributes that were ignored are now refused. An `<element>` refuses `nullQuota`,
  `mimeType` and `distribution`, and takes `min`, `max`, `granularity`, `minLength`,
  `maxLength` only as arguments of `generator=`. `unique` and `weights` stay valid on
  `<element values=>`. A `<variable>` refuses `distribution` beside `generator=`. A
  `<key>` takes `mimeType` only with `type="binary"` or a binary generator, and not
  next to `script=`, `constant=`, `values=`, `pattern=`, `source=` or `string=`.
  Before, each of these was ignored without a message. Migration: move the attribute
  to a `<key>`, or write it in the generator call. `generator="BinaryGenerator"
  mimeType="..."` on a `<key>` now applies the signature; its seeded bytes change.
- A script runs without the future flags of the engine, so its annotations are evaluated
  as in plain Python. A forward reference without quotes in a script annotation, such as
  `nxt: M | None` inside class `M`, now raises `NameError`. Quote it (`"M | None"`).
  A `ClassVar` in a script dataclass now stays a class variable.
- `<generate source="*.wgt.ent.csv">` draws by weight. Before, it read the file as a plain CSV: it returned every
  row once, in file order, with the weight column as a normal column. Now it draws `count` rows by the weights of
  `weightColumn`, with replacement, as EE does, and the output rows have no weight column. It needs `weightColumn`
  and an explicit `count` (`I983`), and it refuses `distribution` other than `random`, `unique`, `cyclic`, `offset`,
  `where`, `columns` and `sourceScripted` (`I983`). A file without the column, without rows or without a weight
  above 0 stops with `I865`, `I867` or `I868`. `weightColumn` on any other `<generate>` source is refused (`I983`).
  Migration: to read the file rows as they are, rename the file to `.ent.csv` (a plain `<generate source=>`
  copies its rows); to sample, add `weightColumn` and `count`.

### Seeded output (regenerate stored seeded output)

- Seeded output of values that a generator draws through the `context` it receives changes. Each such
  generator (`generator="G(context=context)"`) now draws from its own stream, keyed by the seed, the step and
  the element name. Before, all of them restarted from the same seed and drew equal values in one row.
  Unseeded runs, `rng=` generators, keys, variables, scripts and included steps keep their values. Re-capture
  golden files of seeded projects that use such a generator.
- Ten domain data files started with a UTF-8 byte-order mark, so the first value of each
  carried U+FEFF into generated data (#514). The mark is gone from `city_BR`,
  `familyName_AT`, `familyName_BR`, `familyName_DE`, `givenName_female_IL`,
  `givenName_male_CH`, `givenName_male_DE`, `givenName_male_IL`, `street_BR` and
  `street_DE`. Affected contract: seeded output of Person, City and Street for the
  datasets DE, AT, BR, CH and IL, where a draw of a file's first value no longer starts
  with U+FEFF. Migration: none; regenerate stored seeded output.
- `city_US.csv` and `city_DE.csv` lost the leading zero of postal codes (#520). All
  3294 US and 2685 DE short codes are now 5-digit strings (US: MA, NJ, ME, CT, VT, NH,
  PR, RI, VI, NY; DE: SN, ST, TH, BR), for example `06234` Brooklyn and `01067`
  Dresden. The 898 US city names that ended in a lowercase ` city` now end in ` City`
  (`Morgan City`). The header of `city_DE.csv` carried a U+FEFF inside its first cell
  (`state.country.isoCode`); it is removed, and no reader used that column name. `areaCode` is unchanged: it holds the area code without the trunk 0.
  Affected contract: seeded output of Address, City and every model that reads these two
  files, for the `postal_code` of those states and the changed names. Migration: none;
  regenerate stored seeded output.
- City data is normalized for country-specific postal codes and US capitalization
  (#522, #538). `city_AU.csv` no longer includes 716 US rows or four Canadian rows;
  `city_FR.csv` stores only five-digit postal codes, dropping a CEDEX/special-delivery
  suffix when no duplicate plain-code row exists for that department and city. US city
  names use title case, common particles remain lowercase, split `Mc ` names are joined,
  and unambiguous DeKalb, O'Fallon and LaGrange spellings are restored. Affected
  contract: seeded output of Address, City and any model that reads these files for AU,
  FR or US. Migration: none; regenerate stored seeded output.
- `BankAccount.iban` has the structure, length and check digits of its country (ISO 13616),
  the same table as EE: AT, CH, DE, FR, GB, IT, NL and PT. For example, a `dataset="DE"` IBAN
  has 22 characters; before, it had 30 to 32. Seeded IBAN values change for every seed.
  A dataset without an IBAN scheme gives `None`: this holds for US and VN, and for BE and ES,
  which EE also leaves out because their BBAN holds national check digits. No made-up value is
  generated for them. A script that reads the IBAN of such an account must accept `None`.

### CLI and MCP

- `--platform-configs` rejects an explicitly empty value. Omit the option or pass `{}` for no settings.
- CLI exit codes separate usage errors from failed work (#575): an invalid option or argument value found before
  any work exits `2`, a failed operation exits `1`. A malformed, empty or non-object `--platform-configs` value and
  an invalid project name now exit `2` (were `1`), like `--param`. A missing descriptor, an existing project
  directory and a failed run stay `1`. The Python API validates `platform_configs` the same way (#560).
- Every MCP project tool takes a required absolute `project` argument (#496): `datamimic_build`, `datamimic_lint`,
  `datamimic_dry_run`, `datamimic_run`, `datamimic_compile` and `datamimic_decompile`. The fallback to the working
  directory of the server is gone; `--workspace-root` only restricts which projects a call may name, and
  `<project>/.env` is loaded per call. A relative, missing or out-of-root path returns an `input` diagnostic in the
  tool's own result type, not a tool error. A result over 60,000 characters is refused with a hint, never cut.
  Migration: pass the absolute project path in every call.
- The run log is shorter (#554, #578). The per-exporter start lines are gone, page progress and page size log at
  `DEBUG`, and a `Saving` line names its exporter. A statement that fails logs no `Processing ... took` line, and the
  lines of a nested `<generate>` say `'customers|orders' per parent invocation took ...`. In text mode the CLI writes
  errors to stderr; JSON mode keeps stdout. A failed run keeps the log `ERROR` record and the machine-readable
  `Error: [Exxx/Iyyy]` line (#564). Migration: a script that parsed these log lines reads the `Error:` line instead.

### Python and dependencies

- Python minimum becomes 3.11. Python 3.10 compatibility shims are removed.
- Python 3.14 is supported (#515). Dependencies without 3.14 wheels moved up so no
  install builds from source: `pydantic` 2.12.0, `pandas` 2.3.3, `pymongo` 4.15.2,
  `oracledb` 3.3.0, `psycopg2-binary` 2.9.11 and `pyodbc` 5.3.0. A Python 3.14 `csv`
  refuses a delimiter equal to the quote character: `target="CSV(quotechar='|')"` with the
  default separator `|` now fails; set `delimiter` as well.
- Four pinned dependencies move past known vulnerabilities (#608): `pymongo` 4.20.0, `mysql-connector-python`
  26.10.0, `requests` 2.34.2 and `python-dotenv` 1.2.4. PyMongo 4.20 needs MongoDB 4.4 or newer. Migration: run
  MongoDB 4.4 or newer.
- Known vulnerabilities are fixed by `pymongo` 4.20.0, `mysql-connector-python` 26.10.0, `requests` 2.34.2 and `python-dotenv` 1.2.4; PyMongo now requires MongoDB 4.4 or newer.

### Removed APIs

- Unused public helpers are removed. Nothing in CE called any of them.
  - `datamimic_ce.engine.dsl.vocabulary.source_capabilities.serialize_source_capability`: no replacement.
  - `datamimic_ce.engine.io.exporters.core.exporter_state_manager.ExporterStateManager.load_exporter_state`: no replacement; read `get_storage(key)`.
  - `datamimic_ce.engine.runtime.tasks.base.task.ExecutableTask`: no replacement.
  - `datamimic_ce.domains.shared.datasets.locale_registry.get_dataset_code_override`: use `dataset_code_for_locale`.
  - `datamimic_ce.domains.shared.datasets.locale_registry.iter_locale_dataset_overrides`: read `LOCALE_DATASET_OVERRIDES`.
  - `AdministrationOfficeGenerator.pick_founding_year` in `datamimic_ce.domains.public_sector.generators.administration_office_generator`: use `generate_founding_year`.
  - `AdministrationOfficeGenerator.build_website` and `build_email` (same module): no replacement; nothing in CE called them.
  - `datamimic_ce.engine.dsl.model.validation.ModelUtil.check_valid_data_constructor`: no replacement; nothing in CE called it.
  - `datamimic_ce.domains.domain_core.datasets.path.reset_dataset_fallback_log`: no replacement; nothing in CE called it outside one test.

## New

- `datamimic authoring run-project PROJECT` and the MCP tool `datamimic_run_project` run a project for its real
  output (#505). They build first; a Build that is not ready returns `not_run` with the Build result. A run that
  reaches outside the project (database, MongoDB, `<execute>`, a target that is not a project file) is refused
  unless `--allow-side-effects` (MCP: `allow_side_effects`) is set.
- `datamimic_version` and `datamimic authoring version` return `build_protocol: "5.0"` (#496). The build
  protocol (`BuildRequestV5`) is versioned independently of the CE package.
- The MCP tool `datamimic_init` writes the starter project into an empty directory with the same writer as
  `datamimic authoring init`; with it an agent goes from an empty directory to `init`, `build` and `run_project`
  through MCP alone.
- A diagnostic carries `location` with EE's field names (#597): `file`, `line`, `column`, `element`, `attribute`,
  `include_chain` (the files that include `file`, the entry first) and `script_file` / `script_line` for a refused
  `<execute>` library. It is filled for parser, lint and XML syntax errors, errors in included steps and refused
  `<execute>` libraries. `path` is unchanged, and `location` is `null` where CE keeps no source position. It never
  holds a value: `name` stays empty.
- Lint warning `DM320`: an included step sets its own `rngSeed`, which is ignored because the entry owns the seed
  of the run (#472).
- Build proves projects with binary keys (#467). Evidence and diagnostics show a binary value as
  `{"type": "binary", "base64": "..."}`; replay and comparisons use the bytes.
- The agent plugin connects the DATAMIMIC MCP server (#519): `plugins/datamimic/.mcp.json` starts `datamimic-mcp`
  through `uvx` with Python 3.11 to 3.13, and Codex reads it through `.codex-plugin/plugin.json`.

## Fixes

- DM211 no longer rejects a database readback without `count` in an included step whose client the entry
  declares (#493).
- Build no longer reports the exporter's files under `output/` as unread project data, so a project stays `ready`
  after `datamimic run` (#553).
- A malformed `acceptance/build.json` names the file in `path`, and a JSON syntax error says to fix the line and
  column in the message (#552).
- A non-finite captured value (`NaN`, `Infinity`, `1e309`) in dry-run and Build fails with `I958` instead of an
  uncoded `child_execution` (#508). `datamimic run` still accepts these values.
- A dict item of a list that a script builds, and of a bare `<nestedKey type="list">`, has dot access (#441, #478).
  A malformed `*.wgt.csv` fails with `I102` and the file name instead of a raw pandas error or a dropped first
  value (#448).
- Authoring gives correct advice for parent variable reads, a `<variable storage=...>` under `<setup>`, products
  nested two levels deep, unknown columns of a file source (names `columns=`) and ISO date literals in
  `fixed_value` / `allowed_values` (#442, #476, #479). `dry-run`, `run` and Build show the engine warnings `W007`
  and `W008` (#404).
- Bounded execution works on Python 3.13 and 3.14 in root containers (#541).
- The starter has a CSV target, so `datamimic run` writes `output/`, and both `init` commands print the same next
  step (#581). `authoring reference --topic assembly --name starter` echoes the name (#577).
- `--platform-configs` is validated before the run instead of crashing in the runtime (#550).
- Logging writes to the current `sys.stderr`, so an embedding application or test runner that replaces stderr no
  longer gets `I/O operation on closed file` (#579).
- Every authoring command and every `run` / `init` option has help text; `authoring dry-run` and `authoring run`
  read differently in the command list (#574).
- Security: logs no longer contain the text of a database selector, which can hold a parameter or environment
  value (#499). Database operation errors chain a copy of the driver error without SQL text, parameters or driver
  message (#512).

## Known limitations

- `W008` is a static scan; five forms of rebinding entropy names inside a script are known gaps (#439, see
  [migration](../migrations/authoring-errors.md)). Seeded replay in Build stays the hard check.
- Two clients that run `datamimic_init` on the same empty project at the same moment can overwrite a just-created
  starter file (#601). One `init` after another never overwrites.
- `location` is not filled for policy and runtime failures that keep no source position, and it has no `rule`
  field yet.

## For agents and the Platform

The [Codex / Claude Code plugin](../agent_plugin.md) brings the workflow into any repository. Until 5.0.0 is on
PyPI, its setup installs CE from GitHub `development`. An agent authors through the CE CLI, the MCP server that
the plugin starts, or the MCP workflow of a DATAMIMIC Platform project; the live contracts of the runtime are
authoritative. The plugin ends with a model review: structure, counts, key relationships, destinations and the
evidence for each requirement. A requirement that is unsupported or untested stays visible even when Build is
ready.

Models keep field operations and rule parameters visible in the XML. Typed Python functions are for algorithms
that need them, with explicit inputs and decision evidence. The
[complex reference evaluation](../evaluations/complex-authoring-reference.md) is the benchmark for authoring
complex projects.
