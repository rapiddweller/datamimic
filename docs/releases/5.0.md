# DATAMIMIC CE 5.0

CE 5.0 is not on PyPI yet. Until 5.0.0, install from GitHub `development`
using Python 3.11 or newer; CE 5.0 is tested on 3.11, 3.12, 3.13 and 3.14:

```bash
python -m pip install "datamimic-ce @ git+https://github.com/rapiddweller/datamimic@development"
```

Build protocol `5.0` (`BuildRequestV5`) is independent of the CE package version.

## Breaking changes

- Python minimum becomes 3.11. Python 3.10 compatibility shims are removed.
- Ten domain data files started with a UTF-8 byte-order mark, so the first value of each
  carried U+FEFF into generated data (#514). The mark is gone from `city_BR`,
  `familyName_AT`, `familyName_BR`, `familyName_DE`, `givenName_female_IL`,
  `givenName_male_CH`, `givenName_male_DE`, `givenName_male_IL`, `street_BR` and
  `street_DE`. Affected contract: seeded output of Person, City and Street for the
  datasets DE, AT, BR, CH and IL, where a draw of a file's first value no longer starts
  with U+FEFF. Migration: none; regenerate stored seeded output.
- Python 3.14 is supported (#515). Dependencies without 3.14 wheels moved up so no
  install builds from source: `pydantic` 2.12.0, `pandas` 2.3.3, `pymongo` 4.15.2,
  `oracledb` 3.3.0, `psycopg2-binary` 2.9.11 and `pyodbc` 5.3.0. A Python 3.14 `csv`
  refuses a delimiter equal to the quote character: `target="CSV(quotechar='|')"` with the
  default separator `|` now fails; set `delimiter` as well.
- `city_US.csv` and `city_DE.csv` lost the leading zero of postal codes (#520). All
  3294 US and 2685 DE short codes are now 5-digit strings (US: MA, NJ, ME, CT, VT, NH,
  PR, RI, VI, NY; DE: SN, ST, TH, BR), for example `06234` Brooklyn and `01067`
  Dresden. The 898 US city names that ended in a lowercase ` city` now end in ` City`
  (`Morgan City`). The header of `city_DE.csv` carried a U+FEFF inside its first cell
  (`state.country.isoCode`); it is removed, and no reader used that column name. `areaCode` is unchanged: it holds the area code without the trunk 0.
  Affected contract: seeded output of Address, City and every model that reads these two
  files, for the `postal_code` of those states and the changed names. Migration: none;
  regenerate stored seeded output.
- XML is the persisted executable project; DM JSON is transient.
- Project Build replaces persisted Intent/Scaffold authoring. A project is a
  `datamimic.xml` entry, its included steps and `acceptance/build.json`, which holds
  expectations, roles and verification options. A ready Build lists every project
  file it read with its digest.
- Root scaffold/lint/dry-run/reference/capabilities commands move to the typed
  `datamimic authoring` subtree. Legacy Python authoring modules are retired.
- Catalog-backed errors carry stable identity and repair guidance. Some formerly
  generic exceptions now use portable typed exceptions with their native cause.
- Seeded output of values that a generator draws through the `context` it receives changes. Each such
  generator (`generator="G(context=context)"`) now draws from its own stream, keyed by the seed, the step and
  the element name. Before, all of them restarted from the same seed and drew equal values in one row.
  Unseeded runs, `rng=` generators, keys, variables, scripts and included steps keep their values. Re-capture
  golden files of seeded projects that use such a generator.
- Attributes that were ignored are now refused. An `<element>` refuses `nullQuota`,
  `mimeType` and `distribution`, and takes `min`, `max`, `granularity`, `minLength`,
  `maxLength` only as arguments of `generator=`. `unique` and `weights` stay valid on
  `<element values=>`. A `<variable>` refuses `distribution` beside `generator=`. A
  `<key>` takes `mimeType` only with `type="binary"` or a binary generator, and not
  next to `script=`, `constant=`, `values=`, `pattern=`, `source=` or `string=`.
  Before, each of these was ignored without a message. Migration: move the attribute
  to a `<key>`, or write it in the generator call. `generator="BinaryGenerator"
  mimeType="..."` on a `<key>` now applies the signature; its seeded bytes change.
- A script runs without the future flags of the engine, so its annotations are evaluated
  as in plain Python. A forward reference without quotes in a script annotation, such as
  `nxt: M | None` inside class `M`, now raises `NameError`. Quote it (`"M | None"`).
  A `ClassVar` in a script dataclass now stays a class variable.
- `BankAccount.iban` has the structure, length and check digits of its country (ISO 13616),
  the same table as EE: AT, CH, DE, FR, GB, IT, NL and PT. For example, a `dataset="DE"` IBAN
  has 22 characters; before, it had 30 to 32. Seeded IBAN values change for every seed.
  A dataset without an IBAN scheme gives `None`: this holds for US and VN, and for BE and ES,
  which EE also leaves out because their BBAN holds national check digits. No made-up value is
  generated for them. A script that reads the IBAN of such an account must accept `None`.
- `<generate source="*.wgt.ent.csv">` draws by weight. Before, it read the file as a plain CSV: it returned every
  row once, in file order, with the weight column as a normal column. Now it draws `count` rows by the weights of
  `weightColumn`, with replacement, as EE does, and the output rows have no weight column. It needs `weightColumn`
  and an explicit `count` (`I983`), and it refuses `distribution` other than `random`, `unique`, `cyclic`, `offset`,
  `where`, `columns` and `sourceScripted` (`I983`). A file without the column, without rows or without a weight
  above 0 stops with `I865`, `I867` or `I868`. `weightColumn` on any other `<generate>` source is refused (`I983`).
  Migration: to read the file rows as they are, rename the file to `.ent.csv` (a plain `<generate source=>`
  copies its rows); to sample, add `weightColumn` and `count`.
- Unused public helpers are removed. Nothing in CE called any of them.
  - `datamimic_ce.engine.dsl.vocabulary.source_capabilities.serialize_source_capability`: no replacement.
  - `datamimic_ce.engine.io.exporters.core.exporter_state_manager.ExporterStateManager.load_exporter_state`: no replacement; read `get_storage(key)`.
  - `datamimic_ce.engine.runtime.tasks.base.task.ExecutableTask`: no replacement.
  - `datamimic_ce.domains.shared.datasets.locale_registry.get_dataset_code_override`: use `dataset_code_for_locale`.
  - `datamimic_ce.domains.shared.datasets.locale_registry.iter_locale_dataset_overrides`: read `LOCALE_DATASET_OVERRIDES`.
  - `AdministrationOfficeGenerator.pick_founding_year` in `datamimic_ce.domains.public_sector.generators.administration_office_generator`: use `generate_founding_year`.
  - `AdministrationOfficeGenerator.build_website` and `build_email` (same module): no replacement; nothing in CE called them.
  - `datamimic_ce.engine.dsl.model.validation.ModelUtil.check_valid_data_constructor`: no replacement; nothing in CE called it.
  - `datamimic_ce.domains.domain_core.datasets.path.reset_dataset_fallback_log`: no replacement; nothing in CE called it outside one test.
- A Build with open coverage gaps answers `ready_with_gaps`, and `datamimic authoring build` exits with code `3`.
  A Build that passed its run, but whose `coverage` has an open gap (a product without expectation, an unread
  project data file, a declared sink without a sink check, or no `rngSeed`), no longer answers `ready`. It carries the
  same `artifact`, `assurance`, `evidence`, `coverage`, `verification` and `diagnostics` (one `coverage_gap` warning for
  each gap) and the field `action_required`, for example `Ready with 1 open coverage gap (seeded). Do not report
  success until each gap is fixed or explained.` A Build without a gap stays `ready`. Exit codes of `authoring build`:
  `0` ready, `3` ready_with_gaps, `1` rejected or unreadable input, `2` usage error; the text output shows
  `Status: Ready with gaps`. `ReadyBuild` has a new required field `coverage`; `BuildResult` is
  `ReadyBuild | ReadyWithGapsBuild | RejectedBuild` (discriminator `outcome`). `datamimic_run_project` still runs a
  `ready_with_gaps` Build and returns `build_outcome`, `coverage` and `action_required`. Migration: a client that tests
  `outcome == "ready"` sees a gapped Build as not ready, which is the intent; it shows `action_required` and the
  warnings and does not report success. A client that parses `BuildResult` strictly adds `ReadyWithGapsBuild`.
  The authoring eval counts `ready_with_gaps` as not passed.
- Build refuses an acceptance without expectation. A project that generates at least one product and has no check for
  any product (no entry in `expectations`, and no check derived from literal counts, `product_roles` or
  `acceptance_requirements`) is rejected with `missing_expectation`. Build still runs the project; the diagnostic
  (phase `expectation`, path `acceptance/build.json` / `expectations`) follows the diagnostics of the run, and the
  rejection is an `evidence` rejection. Before, `{"version": "5.0"}` was a valid acceptance for such a project.
  Migration: add one expectation, for example `{"kind": "exact_count", "subject": {"kind": "product",
  "product": "orders"}, "count": 10}`. `datamimic authoring init PROJECT` writes a starter project (`datamimic.xml`
  with `rngSeed`, and `acceptance/build.json` with one expectation) that Build proves as `ready`; it never overwrites
  a file and refuses a symlink.

Re-author legacy intent models as projects (see [migration](../migrations/authoring-errors.md));
there is no automated migration. Existing XML execution is
supported. Compile support, bounded-proof eligibility and real external delivery
remain distinct; arbitrary Python execution cannot be made safe by target isolation.

## Agent entry point

The [Codex / Claude Code plugin](../agent_plugin.md) carries the consumer workflow
into other repositories. Shared setup prepares the project environment from GitHub
`development` when needed (until 5.0.0). Authoring uses the CE CLI, the MCP server that the agent plugin starts, or the Platform
project's server-owned MCP workflow. The runtime's live contracts remain authoritative. The plugin returns a model review with structure, counts,
key relationships, destinations and requirement-by-requirement evidence.
Unsupported or untested requirements remain visible even when Build is ready.

Executable models keep native field operations and rule parameters visible.
Typed Python functions handle justified algorithms with explicit inputs and
decision evidence. The [complex reference evaluation](../evaluations/complex-authoring-reference.md) defines
the complex reference gate.
